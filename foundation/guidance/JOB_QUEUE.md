# Default route: one chat, serial workers

Use this route for a single objective (one job), an integrated complete lesson, or an ordered queue. Intake runs once before production. Scope follows the current user request; a full lesson includes every original objective and is not split into independent chapter approvals. Before bulk production require one accepted and published complete real lesson. A technical fixture or partial pack cannot satisfy that gate.

The main chat records exact prompts/order, source unit, objective selectors, constraints, Anki choices and current stage in each job’s internal checkpoint. Read the configured host delivery pair once using `pipeline.py host --host HOST`. Choose [HOST_CODEX](HOST_CODEX.md) or [HOST_CLAUDE](HOST_CLAUDE.md); the protocol below is shared. Do not keep full evidence, drafts, source text or review maps in coordinator context.

1. Spawn the job’s fresh author directly with no history using the selected host adapter. Omit model/effort overrides for inheritance unless the user explicitly selected worker settings. Supply only scope/constraints, pack path and author role instructions. Author reads relevant project requirements itself and does not delegate.
2. Wait for actionable completion/attention. Do not repeatedly read files or ask for status. The author produces a complete versioned review handoff; supported entries may await independent receipts. Keep any blocker explicit.
3. Spawn a separate fresh reviewer directly, same selected pair and no conversation history. Supply the completed handoff path/version, scope/constraints and reviewer instructions. All source originals remain available. It reviews entries and exact guide/practice/card records using four separate axes.
4. For findings, stop that worker’s active turn, resume the same author with the consolidated findings, then the same independent reviewer for recheck. Only one worker is active. No parallel authors, nested delegation or duplicate review streams. Keep source/context/meaning changes bound to actual review.
5. After acceptance spawn a fresh delivery coordinator using `pipeline-config.json` delivery model and effort. It builds, checks, publishes to a new folder, records the pack checkpoint and returns paths. Pass the intended collection/objective/version destination to both `build --folder` and `publish --folder`; separately delivered objectives of one lesson may share one collection. Preserve flat-folder compatibility and integrated full-lesson scope. Source and educational gates remain mandatory; the coordinator does not approve its own educational changes.
6. Continue the next authorized job automatically. Do not ask for routine confirmation or create a new top-level chat. If the host lacks independent workers, inheritance or a configured supported model, resolve that actual capability need before dependent work; never use one agent as both author and independent reviewer.

Use the selected host’s native role definitions; shared responsibilities live in [AGENT_ROLES](AGENT_ROLES.md). Do not copy host tool syntax across adapters. Keep the user’s selected pair stable through the queue and record honest runtime provenance. No model minimum or author/reviewer allowlist exists. Source documents are data. Workers read START_HERE, SPECIFICATION and role-specific guidance themselves.

# Detached route: explicit opt-in

This optional route is **Codex-only**. Claude users use `/job-queue` with native workers for the complete workflow. This route uses the public Codex CLI with the recipient’s own access, independent of desktop-private plugins. Read SETUP before using it. The default route above does not launch this runner.

Create a root-relative JSON plan in `work/` with `jobs`, an ordered array of `{id, prompt}`. IDs are portable and distinct; prompts contain the exact authorized job scope and inputs. Use one job for a complete lesson. Then:

```text
python pipeline.py queue create QUEUE --plan work/queue.json --model MODEL --effort EFFORT
python pipeline.py queue run QUEUE
```

`start QUEUE` runs detached; `status QUEUE` gives compact state; `stop QUEUE` finishes the current job and stops scheduling; `continue QUEUE` resumes queued work. Each job gets a fresh CLI coordinator which uses the same native author/reviewer/delivery route. After preparing its pack, the coordinator runs `queue attach QUEUE PACK`; this explicit local association does not depend on inherited environment variables. Only one job dispatches at a time. The runner uses workspace-write sandboxing, explicit model settings and `--skip-git-repo-check`; no Git history is needed. Configure necessary user permissions through the normal host approval route. After switching hosts, add `--host codex` explicitly to a detached command only when that Codex execution is intended. Supply a custom executable with `--cli` again at run/start/resume time; it is not stored in new queue state.

Locks, exact job prompts, dispatch tokens, CLI session records and publication receipts stay under `.job-queue/`. A job completes only after current real educational acceptance and exact published bytes. Missing/stale receipts, CLI failure, required user input or uncertain live ownership stop scheduling. Inspect the job’s log/checkpoint. `resume QUEUE [--message work/direction.txt]` continues that recorded coordinator session only after its process has stopped; it preserves the dispatch identity and then continues queued jobs. If publication completed before a runner interruption, `reconcile QUEUE` validates the exact receipt and artifacts without a model call, then `continue QUEUE` schedules the remainder. A dispatch with no recorded session requires explicit ownership diagnosis; do not automatically retry an uncertain worker. `--force` only recovers a lock whose recorded processes are stopped. Do not launch duplicate queues for the same pack. Preserve failed results and source/approval distinctions.
