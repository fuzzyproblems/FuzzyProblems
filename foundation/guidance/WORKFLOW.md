# Production workflow

Read the specification and [chapter authoring](CHAPTER_AUTHORING.md). Use the default [job route](JOB_QUEUE.md), one active worker, and no nested delegation.

1. Initialize and complete input onboarding once. Preserve the exact requested scope in the pack checkpoint. Use `prepare --preview` to inspect registered objectives. A complete lesson is a single integrated job, with all chapters in one pack; do not split its review into independently approved fragments. Require the first complete real lesson gate before bulk scheduling.
2. Prepare a new pack. Choose practice types and justify quantities in `quantity_rationale`. Ask once for Anki labels (school optional, course, lesson, task), accepting explicit defaults or delegated choice. Resolve tags before handoff/build; research can continue while a reply is pending.
3. The fresh author reads originals through bounded retrieval, checks reusable dependencies, builds or updates source-linked knowledge entries and completes the guide, declared practice, answers and cards. All facts require supplied-textbook evidence. Include locally taught prerequisite meanings before specialised terms. Cover every clause and necessary prerequisite, not just the provisional component list. Use `coverage.json`, `evidence.json` and claim bindings without parallel planning formats. `entry-inputs` provides exact dependency objects; authors set entries supported, never reviewed.
4. Use `preflight` and repair factual-selection/tag/structure errors. Create exactly one complete `review-handoff`. Send its path, version, job scope and constraints to a fresh independent reviewer; the handoff may include supported entries awaiting review. Source access is unrestricted within supplied textbooks. The reviewer assesses entries and complete applications in one coordinated pass where possible.
5. Reviewer inspects originals, searches beyond selected evidence and records four separate judgments. All guide records, prompts, marking points, options, rationales and cards are included. Copy dependencies by code; never manufacture approvals. After actual entry acceptance, update its receipt/status and run `review-request` for exact current pack dependencies. Only the reviewer may complete `review/independent.json`. Keep failures and gaps explicit.
6. Consolidate substantive findings once in `review/findings.md`. Resume the same author for repairs and same reviewer for targeted recheck; keep one worker active. Use `review-changes` to expose deltas without granting reuse. Notify early only for a blocker invalidating ongoing work. Stop revision once required coverage, source support, depth and quality are satisfied; optional enrichment and cosmetics are not reasons for another pass.
7. A fresh delivery coordinator runs `build`, `check`, then `publish` to a new output version. For a nested destination, pass the same `--folder` to build and publication so textbook links use the checked depth; the full configured destination must match. Separate objectives may share a lesson collection, while a complete lesson stays integrated. `check` requires current educational receipt, unchanged dependencies and exact artifact checks. Current reusable checks avoid repeated full validation. Successful publication refreshes root/group navigation, records exact output bytes and may satisfy the first full-lesson gate. Technical fixtures never satisfy that gate. Preserve existing deliveries; manual relocation to another depth requires a new checked export, not merely a catalogue refresh.

For tutoring, restrict answers to requested scope with reviewed entries and original evidence. Unreviewed or missing support remains explicit. Keep learner mastery/session notes separate from factual acceptance, only when requested. Preserve original inputs, accepted receipts and previous exports. Store detailed work in the pack; return compact progress and actual artifact links.
