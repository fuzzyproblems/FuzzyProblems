# Knowledge and production contracts

The [canonical specification](../SPECIFICATION.md) governs meaning. JSON is UTF-8, inspectable and source-linked. The executable gates are `scripts/contracts.py`, `workflow.py`, `evidence.py`, `qa.py` and `export_privacy.py`. Structural validity never substitutes for independent judgment.

## Identity and source reading

`foundation/intake/catalog.json` maps content-derived `src-<SHA256 first16>` identities to exact relative paths, aliases, roles, inspected identity/edition and one-based original PDF pages. `foundation/intake/units.json` contains complete source-anchored curriculum units and exact learning requirements. `styles.json` contains assessment-style observations only. Printed pagination remains null unless separately verified. See [PDF intake](../guidance/PDF_INTAKE.md).

Preparation creates scoped version-2 dependencies: complete relevant curriculum context and relevant source identity/quality records. Unrelated additions do not invalidate work. Copy the exact `entry-inputs` result into an entry’s dependencies; do not construct hashes by hand. The empty base registries are valid initialization structures; intake records supply the active corpus.

Scopes declare `practice_contract: {version: 2, types: [...]}`. Constructed responses remain in `saqs` with `kind`: short_answer, essay, calculation, data_interpretation or practical. They share the full answer, marking, claim, evidence and review contract. Every declared type and Anki is required; a group can be empty only when undeclared. `explanation` contains the developed supported answer or worked solution.

`anki-tags.json` starts with `pending_user_input`. Use `anki-tags` for the user’s explicit preferences, accepted defaults or delegated choice. Ask once while independent research continues. Tags contain intended School/Course/Lesson/Task labels, canonical objective mappings and useful topic labels. Unicode remains intelligible and colliding labels fail. Tag changes affect exported artifacts, not factual dependencies or stable card IDs.

## Reusable entries

Create `foundation/library/entries/<stable-id>.json`, containing:

- `id`, `version`, `title`, `explanation`, `authors` (internal identities only), `authoring_models` mapping each author ID to `model`, `reasoning`, and an honest `configuration_check` note (including any unverifiable override).
- `objective_links`: objects with objective ID, role (`direct`, `supporting_prerequisite`, `extension`), required depth and inclusion/emphasis rationale.
- `support`: source ID/hash, exact relative source path, original PDF page, exact passages, original-context instructions and `printed_page` (null unless verified).
- `qualifications`, `disagreements`, `limitations` (arrays, including empty arrays when applicable).
- `status`: `candidate`, `supported`, `reviewed`, `gap` or `stale`. An author-supported entry has no independent approval.
- `dependencies`: exact `entry-inputs` dependencies, including scoped `curriculum`, `source_records`, `sources` and `specification_sha256`. The educational-rule digest excludes delivery-only rules.
- `review`: filename of the exact receipt in `foundation/reviews/`, or null before review.

The semantic hash is `workflow.semantic` of the entry excluding top-level `status`, `review`, `dependencies`. It includes every substantive field and qualification. An entry receipt uses `kind: "educational"`, `entry_hash`, exact `dependencies`, reviewer identity/freshness/status fields below, `factual_support: "pass"`, an `evidence_assessment`, and nonempty `independent_searches`. It must result from actual independent original-source review. Source, register or applicable educational-standard changes make the entry stale regardless of its stored label. Entry review does not establish chapter completeness.

## Working pack

Preparation creates `packs/<version>/scope.json`, `content.json`, `coverage.json`, `evidence.json`, and `planning-context.json`. `scope.json` records the exact request and original objective/register dependencies. `content.objectives` must retain the full selected register records in original order. Original sources and the canonical register are never rewritten by authoring.

`content.json` contains:

- `id`, `lesson_label`, `authors`, `authoring_models`, `objectives`, `quantity_rationale`; `entry_dependencies` maps stable entry IDs to current reviewed semantic hashes. Author model records use the entry contract above and require nonempty actual model and reasoning-effort strings, without a tier allowlist (SG-004); do not infer verified runtime settings from a declaration.
- `chapters` in original objective order. Each has `objective_id`, unique simple `file` ending `.html`, `original_number`, complete `wording`, original `pbl_labels`, `title`, `teaching_approach`, `related_objective_ids`, `sections`.
- Each section has unique `id`, `title`, `blocks`. Each block has unique stable `id`, `type`, `text`, `objective_ids`, `entry_ids`, `evidence_ids`. Types: `paragraph`; `table` additionally has `headers` and equal-width `rows`; `figure` additionally has `alt` and `figure` definition. Choose a clear structure suited to the objective and requested form under SG-026; the schema imposes no word/section limit.
- A source figure uses `{kind: "source_crop", evidence_id, rect: [x0,y0,x1,y1], dpi}` in original PDF coordinates. An original educational diagram uses `{kind: "authored_png", file, sha256}` pointing to `assets/<file>`. Its exact bytes and supported caption/concept are independently reviewed. Both types cite original evidence. Only sanitized PNG pixels are embedded in learner HTML.
- `saqs`: unique stable `id`, `prompt`, positive finite `marks`, `marking_points` (`text`, positive finite `marks`, summing to total), `explanation`, `guide_blocks`, `objective_ids`, `entry_ids`, `evidence_ids`. In each marking point's `text`, state how its marks are earned, including allocation within a multi-mark point, required components/count and acceptable alternatives sharing that credit. Score only what `prompt` requests. Use `explanation` to develop the answer and its qualifications without adding unstated scoring requirements. Fractional marks are allowed; they do not cap objective depth.
- `sbas`: unique stable `id`, `prompt`, `marks: 1`, `options` mapping 3–6 letters to text, `correct` letter, `rationales` for **every** option, `guide_blocks`, `objective_ids`, `entry_ids`, `evidence_ids`. The stem and supplied evidence must support one defensible best answer; competing options must be plausible and test the intended distinction. Replace conspicuously implausible distractors rather than adding options. Rationales explain why each option is or is not best under the stated conditions.
- `cards`: unique permanent `id`, `front`, `back`, safe topic `tags` (a list, optionally empty), `objective_ids`, `entry_ids`, `evidence_ids`. Keep a continuing card's existing `id` through wording, ordering and pack-version changes; assign new IDs to genuinely new cards. Fresh independent packs are not automatically revisions. Apply this convention directly in the stable card ID field. Front/Back are text, escaped for HTML; tabs/newlines become safe HTML entities/line breaks. StableID remains the first non-display Anki field. The exporter derives `Lesson::Topic` / `Objective::Topic::1`-style identity tags from the validated register, never `lesson_label` or the pack name. It preserves original numeric strings, adds `::occurrence_N` for repeated numbering after the first occurrence, and rejects empty/colliding normalized lesson names. `Lesson` and `Objective` namespaces are reserved case-insensitively; free topic tags cannot replace generated identity. No original filenames/IDs are rewritten.

Preserve material source-supported distinctions, mechanisms, exceptions and timing in each artifact, including standalone prompts/answers/cards (SG-031); guide context cannot silently qualify a standalone item. Text fields are not arbitrary HTML and never contain packaging/review narration. All educational record IDs are unique across guide, questions and cards. Every real record must link checked knowledge entries **and** exact original evidence. A new application still needs independent review despite those links.

### Claim bindings

Highlights are built only from `passages`, so a claim whose supporting sentence was never quoted cannot be seen in the evidence PDF. A pack whose `scope.json` declares `"claim_binding": {"version": 1}` (preparation sets this for new packs, and authoring does not rewrite `scope.json`) must therefore tile every record's teaching text with `claims` units, and the structural gate refuses to build, request or accept review while that tiling is incomplete. Prepared scopes require the claim-binding declaration; authors must preserve it.

- Each block, SAQ, SBA and card carries `claims`: an ordered list of units whose `text` values, whitespace-normalised and joined with single spaces, reproduce that record's teaching text exactly. Teaching parts in order: a paragraph's `text`; a figure's `text` then `alt`; a table's `text`, then `headers` then each row's cells; an SAQ's `prompt`, then each marking point's `text` in order, then `explanation`; an SBA's `prompt`, then each rationale in option order; a card's `front` then `back`.
- Every unit carries exactly one of `support` or `exempt`. `support` is `{evidence_id, passage}`: the evidence ID must be cited by that record, and `passage` must be one of that evidence record's exact quoted passages, so the reader-visible highlight is named directly. A bound unit is limited to 60 words, which stops one quote from nominally covering a whole paragraph.
- `exempt` is one of `instruction` (question or prompt wording), `framing` (connective or synthesis asserting no new fact), `exclusion` (a statement that an option is not the answer) or `figure` (a caption supported by the embedded source figure rather than by quoted text). Exemptions are declarations, not approvals: they remain visible in `review-view` alongside every teaching unit, and in `review/claim-coverage.json`. The reviewer must judge every exemption against its category; a figure exemption still requires direct support from the inspected original figure.
- The independent receipt carries `claim_binding_assessment`: a short judgment of the declared bindings and exemptions. It is required whenever the pack declares `claim_binding`.
- A binding proves the named quoted sentence is visible, not that it teaches the claim. That remains the reviewer's judgement under the four axes.

Use `review-view PACK` for the complete objective/coverage outline and `review-view PACK --section SELECTOR` for bounded complete records with shared quotations and explicit claim associations. Follow every `next_start`; no sampling. This is a read-only projection of the existing contract, not a new schema or approval. Use `--receipt` after `review-request` to inspect decision fields while copying dependency bindings locally by code. Full claim-coverage and dependency JSON remain diagnostic data on disk, not routine model reading.

`evidence.json` maps stable evidence IDs to `source_id`, full `source_sha256`, integer `pdf_page`, `passages` (exact, directly relevant support for each consuming record, with necessary qualifications), `context` and `limitations`. The source registry supplies exact source path/book identity. Evidence must be from a supplied textbook. Use separate evidence IDs when records need different parts of a page. `selection_checks.select_passage(text, start, end)` requires unique explicit start/end anchors (end excluded); alternatively supply exact quotations directly. It never defaults to a whole page or the first ambiguous caption label. Preserve separately verified printed page information internally if used; exported labels use original PDF pages.

If image-only evidence cannot be highlighted by native text, use `reviewed_coordinates: {quads, receipt}`. Each quad is four original-page points. Its independent `review/<receipt>` has `kind: "coordinates"`, evidence ID, `evidence_hash: workflow.semantic(complete evidence object)`, original-page inspection and geometry assessment, plus the normal reviewer/freshness/pass fields. Do not transcribe image-only text with a model. Record local OCR as unreviewed discovery. Coordinates, if used, need the described source review; they are not required merely to improve highlight appearance. Alternatively use `highlight_optional: true`, no passages/coordinates, and a nonempty `limitations` description to retain an independently supported original page without project highlighting. Exact matching uses NFC/whitespace/soft-hyphen normalization without collapsing scientific symbols.

`review/selection-diagnostics.json` groups selections and consumer IDs. Shared checks union native spans per record/source hash/original page across every evidence ID, and total selected words across pages. Duplicate citations, absent quotations and overlapping selections block handoff/build/acceptance. Review triggers are more than 500 words on a page, at least 85% page coverage with at least 150 words, more than 1,000 words across a record, or unavailable/ambiguous native metrics. These are attention triggers, not length caps or medical judgments; never auto-truncate quotations. Coordinates/unmarked limitations remain explicit and require a disposition. `preflight` exposes these checks without building or approving anything.

`coverage.json` is the existing teaching-contract and coverage representation; do not add a parallel plan or mapping. It has `chapters` in selected objective order and `unresolved_gaps`. Each chapter has `objective_id`, `complete_wording_interpretation`, `depth_rationale`, `prerequisites` and `components`. Interpret every clause of the exact requested objective in these fields at the depth its verbs and subject require. Include every registered component/required-item ID plus source-tested necessary additions; the provisional register is not a completeness ceiling. Each component has `id`, `requirement`, `role`, `guide_blocks` **inside that chapter**, `evidence_ids` actually cited there, `completion_test`, `status`. Completion requires `covered`; otherwise use `partial`, `not_started`, `gap` or `ambiguous` and retain the precise limitation. A complete pack cannot pass with gaps. A named concept or question/card-only content does not establish guide teaching.

## Independent educational receipts

Use one fresh independent reviewer using the user's selected model/effort (SG-004) at a time. Follow [bounded coordination](../guidance/REVIEW_COORDINATION.md). `review-handoff` creates a concise `review/handoff.md`, a pointer `review/handoff.json`, and an immutable `review/handoffs/<version>.json` source/semantic snapshot. Author-supported entries may await receipts at this stage; entry workflow status/review metadata is excluded from handoff semantic change detection. These files are routing only. `review-changes [--handoff VERSION]` writes `review/handoff-changes.json` with changed/removed files, entries and dependency-bound records. It does not create or retain approval. Original source identity mismatches fail. Changes to chapter context/coverage/standards still require assessment even when record IDs are unchanged.

`review/request.json` is the final routing/dependency record and still requires current independent entry receipts. `review-request` writes exact `review/inputs.json` in the same call and includes an unapproved receipt scaffold in the request itself: exact inputs, chapter/component IDs and guide/evidence mappings, with all judgments unset. The reviewer can copy this file to `review/independent.json` and fill the existing receipt fields below after actual independent review. Copy the mechanical bindings without printing or reconstructing them; inspect the required records, maps and source/content fields needed for judgment. Routing fields may remain in the internal receipt. The command never writes or rebinds `independent.json`, copies prior decisions, or selects reviewed/retained records. Regenerating a request leaves an existing receipt stale until the reviewer assesses the revision and explicitly writes a current receipt.

- `kind: "educational"`, `mode: "full"` (default), `reviewer: {id, model: "<actual model>", reasoning: "<actual effort>"}`, `fresh_context: true`, `status: "pass"`, `unresolved_findings: []` only when justified. Reviewer ID must differ from authors. Failures/needs-revision receipts remain honest and block publication.
- `inputs`: exact object already included by `review-request`; `guide_only_assessed: true`; `reviewed_records`: every current guide/SAQ/SBA/card ID actually reviewed. The request's `required_records` identifies work, while `reviewed_records` starts empty and must be supplied by the reviewer. Reviewing a question includes its stem, marking points, answer, options and all explanations.
- `verdicts` with four separate keys: `factual_support`, `chapter_coverage`, `explanatory_depth`, `educational_quality`. All must independently pass.
- `selection_review`: `{key, verdict: "pass", exceptions: {FLAG_ID: "specific justification"}}`, using the unset scaffold from `review-request`. The verdict assesses selection relevance for every current consumer during the same source review; reasons are required only for accepted flags and must cover all consumers grouped under that flag. The exceptions keys must exactly match current flags. Its key binds content/evidence, original hashes, coordinate receipts, SG-035, diagnostic policy/code and native-text runtime; old receipts cannot supply an unperformed precision judgment. This is part of the existing receipt, not a fifth educational axis or another review pass.
- `review/claim-coverage.json` remains an advisory diagnostic on disk, never approval. Routine `review-view` sections expose applicable acronym gaps, incomplete quotations and records without quoted spans alongside the teaching and support. Judge every flag; give reasons in the consolidated findings where action or explanation is needed. A quiet report does not prove support. Fetch surrounding original text to resolve context. The JSON-only check itself makes no model calls.
- Nonempty `original_pages_inspected` and `independent_searches`. Routine privacy and presentation receipts are not required. Record actual pages/queries/findings, including searches beyond selected evidence, not boilerplate promises.
- `chapters` matching the coverage order: objective ID, four separate verdicts, `teaching_approach_assessment`, `complete_wording_assessment`, and `components` matching the coverage map. Each component records ID, exact guide-block/evidence IDs, four verdicts, a specific `rationale` for coverage/depth and `evidence_assessment` for source support and material qualifications. Give concise actual reasons for each decision without repeating the same explanation across fields or outputs.

Apply SG-027's coverage/depth judgment within this same independent review, against the original objective, curriculum learner level and source context, independently of the author's map or completion tests. Use the existing component verdicts and `rationale` to judge whether the chapter teaches the required meaning and connections, rather than merely containing the categories; retain separate source-support judgments. Record material omissions in `complete_wording_assessment` and batch actionable corrections with their source context in the existing consolidated findings, retaining unresolved defects in `unresolved_findings`. Use context already read and targeted additional textbook lookup only as needed to resolve substantive gaps; access to all supplied originals remains available. Re-review corrected coverage/content through the existing coordination route, including SG-028–031 assessment/card requirements, and stop when objective-relevant gaps and existing acceptance requirements are resolved. Do not add a second pass, checklist, per-term commentary or keyword validator.

## Targeted revisions

Preserve an actually accepted prior educational receipt as `review/<baseline-name>.json`. Do not replace that baseline. The passing complete gate automatically stores its exact completion snapshot in `review/accepted/<receipt SHA>.json`; that snapshot must accompany the baseline when making a new working version. A receipt that never passed the complete gate cannot donate approvals. After changes:

```bash
python pipeline.py review-request PACK --baseline baseline-name.json
```

A **fresh** reviewer may use the request's `mode: "targeted"` scaffold, which includes `baseline_receipt`, its exact `baseline_sha256`, current `inputs`, and exact `delta`. The reviewer supplies the same required current four-axis chapter/component judgments. `reviewed_records` must equal every changed/new record; `retained_records` must explicitly select the unchanged records with unchanged original evidence, source/objective and entry dependencies. Both lists start empty; `retained_record_candidates` grants no approval. Removed records appear in the delta and cannot hide coverage losses.

Require substantive `current_standard_assessment` and `meaning_and_depth_assessment`. A presentation-only change can reuse factual support after that judgment; changed meaning cannot masquerade as unchanged. Standards/coverage/wording changes still require complete current chapter judgments. There is no routine presentation receipt. CSS/template-only changes retain factual acceptance when substantive inputs are identical. Neither script nor author synthesizes approvals from the baseline. Entry changes receive entry-specific factual review, which can share one source-reading pass with review of their completed applications.

## Builds, artifacts and publication

`build.json` is a non-approval dependency snapshot with explicit learner allowlist and file hashes. `citation-occurrences.json` records chapter blocks/figures in original objective/section order, then SAQ answers, SBA answers, then Anki Sources; within each record use its declared evidence order. Copy every occurrence, repeating pages. A citation reference block may link original, unmarked and marked versions of that same occurrence. Internal evidence/layout caches are bound to actual inputs, runtime and output bytes.

Learner files are exactly `index.html`, every declared chapter file, `practice.html`, `answers.html`, `anki.html`, `anki.tsv`, `anki-note-type.json`, `evidence-unmarked.pdf`, `evidence-highlighted.pdf`. No review/maps/logs/manifests are delivered. Source URLs are relative; book/page labels are readable. Rendering and sanitization preserve original source fidelity. Ambiguous/incomplete highlight geometry produces a recorded unmarked-page limitation. Wrong/absent quoted support, damaged source content, missing teaching or mismatched citations still fail.

`validation/artifacts.json` caches deterministic exported-content, table/answer, citation/link, figure and Anki checks against exact input/output and validation-code hashes. Normal `qa` runs this HTML/data route with zero renders. Optional `qa --render [--files ...]` creates desktop-only diagnostics for one to three selected files in `validation/desktop/` and a `validation/desktop.json` record. It is an offline diagnostic, not a live browser test. Current detected missing teaching blocks acceptance; cosmetic issues do not. Model inspection is targeted when useful, never every-page by default. No mobile/print or independent presentation receipt is required.

`validation/completion.json` joins current independent educational review, scope, dependencies, artifact hashes and content/citation checks. `validation_key` binds reusable validation to exact bytes, current code and review. `highlight_limitations` preserves any unmarked occurrences. `publication.json` binds the new output folder and exact-byte comparison; publication refreshes the catalogue. `foundation/production-gate.json` still requires a complete real lesson with all educational gates. A technical fixture cannot create it.

Templates project educational fields and neutral metadata by construction. Code resolves paths at runtime; stored project paths are root-relative and browser links are file-relative. Keep receipts immutable. Delivery-only changes retain factual acceptance only when every educational dependency remains identical. Changes to educational rules invalidate affected approvals.

Synthetic test receipts are a distinct kind accepted only in disposable marked temporary roots with explicit test calls. The normal production CLI rejects them; they cannot satisfy the real lesson gate. Tests leave no authored content, receipts or output in production areas.

Runtime provenance is provider-neutral. Existing `model`, `reasoning` and
`configuration_check` fields remain compatible. Record observed values only;
use the explicit string `unverified` and explain unavailable exposure. Optional
`host`, `requested_model` and `requested_reasoning` distinguish host requests from
observation. Author/reviewer IDs are logical job IDs, never account names. See
[shared roles](../guidance/AGENT_ROLES.md). These internal fields are never learner
export fields. Host switching does not itself change educational dependencies.
